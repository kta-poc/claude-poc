# 0004. AI駆動開発ワークフローにテストリスト先行のテストファースト方式を採用

Date: 2026-07-03
Status: proposed

## Context and Problem Statement

エージェント(Claude Code)に実装を大きく任せるAI駆動開発では、LLMの出力は本質的に信用しきれないため、機械的に検証できるフィードバックループが品質の前提になる。テストはその中核だが、実装とテストを同じエージェントが書くと「実装の誤解がテストに写り緑のまま固定化される」「落ちたテストをテスト側の修正で通そうとする」という自己採点問題が生じる。人間のレビューをどこに置き、エージェントをどういう手順で動かすかの方式決定が必要である。

## Decision Drivers

- 人間のレビュー工数は有限であり、量の多い実装コードの全量レビューはAI駆動の速度メリットを打ち消す
- テストは仕様の写像であり、実装コードよりレビューが速く判断しやすい
- 仕様の誤解はテスト作成より前(設計・仕様の確認段階)でしか安く直せない
- 仕様の検討はgrillingスキルによる対話で行う運用が既に定着しており、その合意を後から参照できる成果物に残したい
- エージェントが書くテストは、指示がなければ過度に抽象化されレビュー装置として劣化しがち

## Considered Options

- 実装後レビュー方式: エージェントに実装させ、人間が実装コードとテストをまとめてレビューする
- テストファースト方式: テストコードを先に書かせ、人間はテストコードをレビューしてから実装させる
- テストリスト先行のテストファースト方式: テストコードの前に日本語のテストリストを挟み、人間はリストをレビューする

## Decision Outcome

Chosen option: 「テストリスト先行のテストファースト方式」。人間の関与を「仕様(テストリスト)の承認」という最も読む量が少なく判断しやすいゲートに圧縮でき、grillingによる仕様検討の終着点をテストリストにすることで仕様レビューとテストレビューを1つに統合できるため。

ワークフローの全体像:

1. **設計・仕様の確認** — grillingで仕様を対話的に固め、合意事項を「検証する振る舞いの一覧(テストリスト)」として文書化する(正常系・異常系・境界値)
2. **テストリストの承認** — 人間がリストをレビューする。これが実質の仕様承認ゲート
3. **テストコード作成** — 承認済みリストに沿ってエージェントがテストを書く
4. **実装** — テストが通るまでエージェントが自律ループで実装する。実装フェーズではテストファイルを変更しない(変更が必要と判断したら停止して人間に確認)
5. **実機検証** — ユニットテスト緑で終わらせず、実際にアプリを動かして当該機能を通す

テストコードのレビュー容易性を保つ規約(CLAUDE.mdガイドラインの記入例に反映済み):

- テスト名(Goのテーブル駆動ケース名、JSの `describe`/`it`)は振る舞いを表す日本語の文にする
- 1テスト1振る舞い。共通化ヘルパー・モックは最小限にし、1ケースを上から読んで完結させる

採用しないと決めたこと:

- Gherkin/Cucumber等の仕様記述ツールの導入(命名規約とテストリスト運用で同等の効果が得られるため初期には不要)
- テストと実装のコミット/MR分離の義務化(今回は採用せず、必要になったら再検討)

### Consequences

- Good: 人間のレビューが「テストリストの承認」に集中でき、実装コードの全量レビューが不要になる
- Good: grillingの合意が会話の中に埋もれず、テストリストという再利用可能な成果物になる
- Good: テスト変更禁止ルールにより、エージェントがテストを弱めて通す自己採点問題を構造的に防げる
- Bad: 品質の源泉がテストリストの質に一点集中するため、リストのレビューが浅いと誤った仕様のまま全工程が進む
- Bad: ユニットテストで守れない統合の継ぎ目(DB・外部API・環境)は残るため、実機検証ステップを省略できない
- Bad: 探索的な作業(仕様がまだ固められないプロトタイピング)にはこのフローは重く、適用範囲の判断が必要

## Pros and Cons of the Options

### 実装後レビュー方式

- Good: フローが単純で、エージェントへの追加指示がほぼ不要
- Bad: レビュー対象が量の多い実装コード全体になり、人間がボトルネックになる
- Bad: 仕様の誤解が実装完了後に発覚し、手戻りが最も高くつく

### テストファースト方式

- Good: 実装より先にテストをレビューでき、自己採点問題をある程度防げる
- Bad: レビュー対象がテスト「コード」なので、仕様の抜け(足りないケース)の指摘がコードを読める人に限られ、リストより時間がかかる

### テストリスト先行のテストファースト方式

- Good: レビュー対象が日本語の箇条書きになり、最も速く・広い関係者で仕様の妥当性を判断できる
- Good: 仕様レビューとテストレビューが1ゲートに統合される
- Bad: テストリスト→テストコードの変換ステップが増え、リストとコードの乖離を確認する手間が残る
